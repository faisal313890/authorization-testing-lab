KNOW THE POLICY

Four identities. Two tenants.

Who can do what?

  • Members read and edit only their own invoices.
  • Admins read and edit invoices in their own tenant.
  • Only admins list users, limited to their own tenant.
  • Profiles accept display_name only. Clients cannot set role or tenant.
  • Anonymous requests cannot use protected operations.

Both modes use server-held identities. Weak mode deliberately omits selected authorization checks.

Why the corrected mode differs

Object operations apply an ownership or admin check together with a tenant check. Admin operations require a server-held role and filter returned records by tenant. Profile updates accept an explicit field allowlist.

The role-assignment exercise includes a second request to the admin endpoint. The tenant-assignment exercise reads the profile again to check whether protected state changed.

Coverage and interpretation

  • This lab tests its own invented policy and records. It does not inspect other websites.
  • Persona switching is a training control. Credential validation, MFA, production sessions and TLS are outside scope.
  • These finite cases do not prove the absence of other authorization bugs, race conditions or information leaks.
  • IDs intentionally remain visible. Hardened mode returns 403 for known forbidden invoices and 404 for absent invoices; object-existence hiding is not implemented.
  • No database or external API. State stays in server memory; reports stay in the browser until exported. Restarting clears all sandboxes.
